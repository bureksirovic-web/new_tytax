# G5-05: a backup must not carry the account id (src/lib/db export/import, owned by G2)

**From:** G5 (refuter fixes), 2026-09-27. **To:** G2 (`src/lib/db/**`, `src/lib/{import,export}/**`).

## What
`exportBackup()` writes each profile with its `accountId` (the Supabase auth uid of the account that
claimed it). `importBackup()` restores it unchanged. Imported on a device signed in as another account C,
those profiles belong to account A: the sync adapter never pushes them (it must not: they are A's rows,
and A's ids are taken on the server), so C's later edits on the imported profile never leave the device.

## Evidence (reproduced 2026-09-26 against local Supabase)
Refuter run: `A sync {"pushed":2,…}`, `backup profile accountId <A's uid>`, `C sync {"pushed":0,…,"status":"idle",…,"pending":3}`,
server rows for C: 0. Now pinned by `src/lib/sync/__tests__/conflicts.sync.test.ts`
"a backup of account A imported while C is signed in …" and `adapter-conflicts.test.ts` "ops of another account …".

## Mitigation in G5 (in place)
The run no longer reports `idle`/synced while such ops wait: status `error`, `lastError: 'other_account'`
(UI key `sync.error.other_account`), no `lastSyncedAt`. Tenant isolation already held.

## Proposed change
In `exportBackup()` omit `accountId` from every profile (the account is a property of the device's
sign-in, not of the data). Optionally, in `importBackup()`, when a profile id already exists on the
server under another account, give the imported profile and its records new ids (the ids are global
primary keys; see migration 002 "Ids"). Without the second part, importing someone else's backup while
signed in to your own account fails the push with 42501 (dead letters), which is the correct outcome.
