# G5-04: `applyRemote` must not compare server time with device time (src/lib/db, owned by G2)

**From:** G5 (refuter fixes), 2026-09-27. **To:** G2 (`src/lib/db/**`). G5 applies it at INTEGRATION if still open.

## What
`applyRemote` in `src/lib/db/repo/transfer.ts` (lines 124-134) skips a pulled row when
`remote.updatedAt <= local.updatedAt`. `remote.updatedAt` is the server's `updated_at` (set by a trigger,
server clock); `local.updatedAt` is stamped by the device clock (`ctx.stamp()`). The two clocks are not
comparable:
1. **Clock ahead:** a device whose clock runs ahead by more than the gap between two edits never takes
   another device's newer edit, and later pushes its stale row back over it (data loss on the server and
   on the other device). Both devices report `idle`.
2. **Clock behind, edit during a pull:** the adapter used to read the pending-op set before calling
   `applyRemote`, outside its transaction. An edit that commits in between is overwritten by the older
   server copy, and the queued op then pushes the overwritten value.

The contract (`src/contracts/sync.ts`) says "last-write-wins on server `updatedAt`", and
`docs/v2/sync-schema.md` says the client value is ignored.

## Evidence (reproduced 2026-09-26, refuter run; tests red before the G5 mitigation)
- `src/lib/sync/__tests__/adapter-conflicts.test.ts` "a device whose clock runs 1 h ahead …": `expected +0 to be 1`
  (B pulled nothing and kept 81 while the server had 82).
- same file, "a local edit that lands while a page is being applied … clock is behind": `expected 85 to be 99`.
- live: `src/lib/sync/__tests__/conflicts.sync.test.ts` (npm run test:sync), same two cases against local Supabase.

## Mitigation in G5 (in place, `src/lib/sync/pull.ts`)
Per pulled page, inside `repo.transaction`: read the whole outbox, drop rows of records with a queued op,
drop rows whose content equals the local copy, and hand the rest to `applyRemote` with `updatedAt`
raised to 1 ms past the local value when the server's is not already later. Cost: one `exportBackup()` per
run that pulls rows (to read local copies), and local `updatedAt` values that differ from the server's.

## Proposed change (then G5 drops the `updatedAt` rewrite and the `exportBackup()` read)
Server wins for every record without a queued op, checked in the same transaction:

```ts
export async function applyRemote(ctx, table, records) {
  // …validation as today…
  return ctx.write(async () => {
    const pending = new Set(
      (await ctx.db.syncQueue.where('table').equals(table).toArray())      // or a [table+recordId] index
        .filter((op) => !String(op.lastError ?? '').startsWith('permanent:'))
        .map((op) => op.recordId),
    );
    let applied = 0;
    let skipped = 0;
    for (const remote of records) {
      if (!isDataRow(remote) || !Number.isFinite(timeOf(remote.updatedAt))) { skipped += 1; continue; }
      if (pending.has(remote.id)) { skipped += 1; continue; }   // the local change is pushed next and wins
      await target.put(remote);                                  // no device-clock comparison
      applied += 1;
    }
    return { applied, skipped };
  });
}
```
`ApplyRemoteResult.skipped` then means "rows ignored because the record has an unsent local change"
(a doc-only change to `src/contracts/sync.ts`, frozen: record it here).
